# Compact combined-architecture study

Aim: test an actual closed-loop combination of the earlier action-aware network controller and the v3 host detector. The saved model and accepted deployment records define this evaluation. Optional task verification is outside this study.

All ten nodes use instruction-emulated Z1 firmware and actual UDP/RPL packet transport. A root transport authenticates data/reports and exports received observations to a host gateway. The gateway runs the earlier source-work/receipt/lease accounting and bounded query/repair policy, plus the HMA detector. Decisions return to the root and become actual authenticated UDP queries and repair grants. This is a simulation gateway interface, not modeled counterfactual delivery. Inference wall time is outside simulated time; root command polling/packet delays occur in simulated time. No MCU neural inference, FIT result or hardware attestation is claimed.

Bring-up attempts are excluded. Source runs1111/1112 contain benign normal and mixed activity, with0/1500authorized CPU rounds. Calibration1113/1114 contains benign loss and legitimate activity with500/1000authorized rounds. Only these deployments can fit resource prediction, model preprocessing or thresholds. V3 classifier/GRU weights retain their prior pretrained host source training, including attack labels. This additional supervision must be disclosed against benign-only comparison methods.

Final matrix: seven policies × three contexts × two fresh deployment blocks,42runs of900seconds. Deployment1151uses bypass layout/target2;1152uses grid/target3. Both benign authorized activity,250-round hidden CPU with selective forwarding, and sparse4s/60s CPU misuse with legitimate traffic changes/selective forwarding/loss are covered. Attack interval400–700s; authorized job300–780s. One seed per topology confounds topology and seed, so no topology-generalization claim or narrow confidence interval is supported.

Policies: combined; earlier network controller(no HMA use, equal telemetry instrumentation); CIPHER-style correlation-grouped LSTM autoencoder adaptation; CONTRAST-style CPU/TX LSTM autoencoder adaptation; combined without authorized-work context; without response/action accounting; without slow residual memory. All have the same authenticated transport, mandatory telemetry,480B/10s discretionary reservation, helper quota/leases and controller. Component removals retain frozen full-model settings. Named detectors are architecture adaptations to the available inputs, not complete original distributed frameworks or exact published results.

Final detector/model/policy settings freeze before opening final run outcomes. Do not adjust them on final seeds. Report actual application offered/unique delivered/worst-source delivery; attempted mandatory/discretionary bytes and cap compliance; per-device host warnings, onset and recovery; complete benign-run alarms; missing evidence/coverage; sparse burst coverage; and actual command receipt/execution. Offered work retains blocked/unreachable attempts. Packet copies are deduplicated. Correlated observation counts are not independent deployment sample sizes.

The maintained network model only prioritizes investigation; HMA warnings also prioritize queries and exclude suspicious helpers, but alone do not disconnect a device or prove malicious intent. Absence of warning is not certified host integrity. Missing source/monitor evidence remains unresolved. Crypto authenticates measurements, not their truth. The host-monitor isolation assumption and benign initial reference period remain.

Acceptance clarification before final completion: a stack failure or broken signed-wire/session invariant is a rig failure. A helper rejecting an expired/overlapping capability is a failed repair outcome and must be counted, not used to exclude a final run. Software AES is checked against a known vector in every mote; per-wire HMACs and exact issued/sent command sequences are independently verified. Rejection counts are retained even if nonzero. Earlier all-repair authentication failures during bring-up were excluded before final freezing and fixed by the verified AES128 software path.

Forwarding exposure is an observed property: a configured relay may have no transit packets to drop under a particular routing realization. Such cases remain in the dataset with their actual drop count(including zero); they support host-misuse evaluation but cannot establish protection against an exercised forwarding attack. No final deployment/target is changed after observing this outcome.
